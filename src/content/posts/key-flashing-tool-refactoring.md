**项目目录：** `D:/project_afeng/key/`

**重构结束时间：** 2026-08-25

**定位：** 面向开发与生产人员的单机、单设备终端烧录工具。

## 1. 重构目标与边界

原程序 `D:/project_afeng/原key烧录程序/main_freq.py` 是“本地网页 UI + WebSocket + CDNET 串口 + 云端取密钥”的烧录程序。网页前端一旦未正常启动，原先的 UI 更新链路可能阻塞烧录流程。

本次采用最小重构：将当前 Key 设备的烧录流程独立为终端程序，不再启动浏览器或依赖网页/WebSocket；保留已验证的 CDNET 协议、寄存器、云端接口字段及烧录顺序。

本次不做：

- 不改设备协议、寄存器地址、波特率、目标地址和云端业务接口；
- 不支持多设备并行烧录；
- 不重写为完整状态机、数据库或 Web 服务；
- 不删除原烧录程序及其网页相关文件；
- 不把历史的 Wi-Fi 校验流程迁入当前工具。

## 2. 最终程序结构

```text
send_key.py
  ├── 串口发现与连接
  ├── CDNET/CSA 收发
  ├── 设备 CID 与状态读取
  ├── 云端密钥获取与内存缓存
  ├── 密钥写入、回读验证、重启
  ├── 烧录日志
  └── 连续烧录主循环

pycdnet/
  └── CDNET 串口、协议解析、分发与端口发现
```

运行入口：

```powershell
py -3.10 .\send_key.py
```

## 3. 保持兼容的关键参数

| 项目 | 当前值 | 说明 |
| --- | ---: | --- |
| 设备筛选 | `USB VID:PID=2E3C:5740` | 用于发现目标串口 |
| 波特率 | `20_000_000` | 原设备通信参数 |
| CDNET 目标地址 | `00:00:10` | 保持原协议 |
| 本地端口 | `0x40` | 主业务通信端口 |
| CSA 端口 | `0x05` | 寄存器读写端口 |
| 调试端口 | `9` | 后台持续读取，避免调试帧堆积 |
| 重启寄存器 | `0x0005` | 写入 `0x02` 请求重启 |
| 密钥状态寄存器 | `0x02DA` | 写入 `0x80` 提交烧录 |
| 密钥数据寄存器 | `0x02DB` | 8 字节密钥数据 |
| 单次通信超时 | 1 秒 | `TIMEOUT` |
| 离线等待超时 | 10 秒 | `OFFLINE_TIMEOUT` |

## 4. 当前烧录流程

```text
等待设备
  → 读取设备信息，解析 CID
  → 等待设备启动完成（3 秒）
  → 读取密钥状态
      ├─ 0x01：已烧录，跳过写入、记录日志、等待设备离线
      ├─ 0x00：向内存缓存/云端取得 8 字节密钥
      │          → 写入密钥
      │          → 写入 0x80 提交状态
      │          → 回读密钥和状态
      │          → 二者均验证通过
      │          → 写入重启命令
      │          → 记录成功日志
      │          → 等待设备离线
      └─ 其他：记录失败日志并报错，要求拔出故障设备
```

成功或“已烧录跳过”分支会返回 `"completed"`，主循环直接进入下一轮，避免此前内部和外部两次等待设备离线。

## 5. 本次主要改动与收益

### 5.1 终端化运行

- 新入口为 `send_key.py`，不启动网页、WebSocket 或浏览器。
- 终端直接显示设备 CID、密钥状态、写入及验证结果、离线等待和异常原因。
- 处理 `Ctrl+C`：入口捕获 `KeyboardInterrupt`，正常显示“程序已停止”。

### 5.2 串口发现与端口 9 处理

- 启动时用 VID/PID 查找实际串口；找不到时打印当前检测到的端口及排查提示。
- 修复将 `USB VID:PID=...` 字符串直接交给 pyserial 导致的 Windows 文件名语法错误；实际打开解析出的 `COMx`。
- 创建端口 9 的独立后台读取线程。端口 9 为设备调试帧，本工具不使用其内容；持续读取后不再由主通信路径积压并反复出现 `port 9 not found, drop`。
- `pycdnet` 串口发送在断线时会返回错误，避免继续尝试向关闭的串口写入；这是 `send: Attempting to use a port that is not open` 问题的基础修复。

### 5.3 烧录可靠性

- 对 CSA 读写响应、响应状态和响应长度进行检查。
- CID/固件信息按明确的正则格式解析，非法文本会报出解析错误。
- 云端响应必须为成功状态、十六进制格式且长度严格为 8 字节；最多重试 3 次。
- 写入后回读 `0x02DB` 和 `0x02DA`，同时验证密钥内容和状态；不再只依赖状态位。
- 成功分支先发送重启命令，再记录成功日志；日志 I/O 出错仅打印警告，不会阻断已经发送的重启命令。

### 5.4 密钥缓存与日志

- 采用与原程序 `ip_cache` 对齐的内存 FIFO 缓存：最多 100 条 `CID → 密钥` 映射。
- 缓存仅在进程存活期间有效，程序重启后从 0 条开始，这是预期行为；不再把密钥明文持久化到磁盘。
- 缓存命中只省去云端请求，仍会按流程对未烧录设备写入和回读验证。
- `log.txt` 位于 `send_key.py` 同目录，记录格式兼容原程序：

```text
YYYYMMDDHHMMSS <CID>: burned: True/False, wifi: False None
```

- 当前设备不做 Wi-Fi 测试，因此 `wifi` 字段固定为 `False None`，保留该字段仅为兼容既有日志格式。

### 5.5 Windows / Linux 运行基础

- 端口发现基于 `pyserial` 的枚举结果，能够识别 Windows 的 `COMx` 和 Linux 的 `/dev/ttyUSB*`、`/dev/ttyACM*`。
- 已提供 `requirements.txt`、`setup_windows.bat`、`setup_linux.sh` 和 `DEPENDENCIES.md`，用于安装 Python 依赖与运行前准备。
- 实际运行仍需要：Python 3.10、设备驱动、访问串口的权限，以及满足 20 MHz 波特率的 USB 串口硬件。

## 6. 与原程序的主要差异

| 项目 | 原程序 `main_freq.py` | 当前 `send_key.py` |
| --- | --- | --- |
| 操作界面 | 浏览器网页 + WebSocket | 终端输出 |
| 依赖网页 | 是，UI 更新会等待前端 | 否 |
| Wi-Fi 测试 | 包含历史 AP/Wi-Fi 校验分支 | 不执行，仅保留日志字段 |
| 密钥缓存 | 内存 `ip_cache`，100 条 | 内存 FIFO 缓存，100 条 |
| 密钥回读 | 主要检查状态 | 同时检查状态和 8 字节密钥 |
| 日志时机 | 下一轮开始时记录上一轮状态 | 当前分支即时记录 |
| 重启方式 | 寄存器重启，且存在历史 HTTP 重启调用 | 仅寄存器 `0x0005 = 0x02` |
| 出错提示 | 混杂调试输出与 UI 状态 | 明确显示超时、失败原因和等待拔出 |

## 7. 已撤销的方案

曾评估“Linux 拔插后串口路径从 `/dev/ttyUSB0` 变为 `/dev/ttyUSB1` 时，用 VID/PID 重新发现设备”的修改。该修改已经按要求撤销：

- 当前 `cdbus_serial.py` 未保留 `reconnect_filter` 参数；
- 当前运行仍以首次解析出的实际端口路径进行重连；
- 不能将 Linux 路径变化后的自动重连视为已交付能力。

## 8. 已知限制与后续风险

1. `wait_device_offline()` 当前将一次设备信息读取超时视为离线。通信短暂抖动可能被误判为设备已经拔出或重启完成；这是原程序也有的行为，本轮未扩大范围修复。
2. Linux 设备重新插入后如果节点路径变化，当前串口重连不保证成功；重新启动程序通常可重新发现设备。
3. 存在多个匹配同 VID/PID 的串口设备时，端口发现会选取第一个匹配项，不适合多工位或多烧录器并发使用。
4. 云端 URL、任务标识和密码仍在源码配置中。应限制仓库访问权限，后续可改为环境变量或受保护的本地配置；本次为保持原业务接口未变更。
5. `CDNetIntf` 为后台线程，目前主程序只停止串口线程。若后续要完善资源回收，应先验证其队列阻塞语义，不能直接调用可能长期阻塞的停止方法。
6. 当前无自动化硬件测试；语法和模拟流程检查不能替代真实设备、云端和 USB 拔插测试。

## 9. 验收与日常使用建议

每次发布前至少完成：

1. `py -3.10 -m py_compile .\send_key.py .\pycdnet\cdnet\dev\cdbus_serial.py`
2. Windows：无设备启动提示、已烧录设备跳过、未烧录设备写入和回读、设备离线后的下一轮识别。
3. 检查 `log.txt` 是否产生一条与操作结果对应的记录。
4. 断线或验证失败时，确认终端提示“等待当前设备离线”，拔出设备后可以继续。
5. Linux：确认用户属于可访问串口的用户组，检查设备节点权限，并实测一次实际硬件连接。

## 10. 后续工作建议

本轮重构至此结束。若后续继续，建议按风险从低到高处理：

1. 修正离线判断：连续多次读取失败后才判定离线。
2. 增加设备选择/唯一性校验，避免多设备时误选端口。
3. 把云端凭据移出源码并建立安全的部署配置。
4. 在真实 Linux 环境验证端口权限、20 MHz 波特率和拔插重连，再决定是否恢复 VID/PID 重连方案。
5. 有明确多型号需求后，再抽象设备 Profile/Adapter 和完整状态机；不建议在当前稳定单机工具上提前引入该复杂度。
